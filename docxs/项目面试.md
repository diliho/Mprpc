# MPRPC 项目面试 Q&A

> 项目简介：基于 Muduo+Protobuf 的简易 RPC 通信框架（个人学习实践项目）

---

## 1. 自定义二进制通信协议

**简历描述：** 基于 Protobuf 定义 RPC 服务接口与通信协议，结合 Muduo Reactor 多线程网络库实现服务端请求分发与客户端异步调用，自定义 4 字节长度头 + Proto 消息的二进制通信协议。

---

### Q: 你们的 RPC 通信协议是怎么设计的？为什么不用 HTTP 而自己定义协议？

**A:** 我们的协议格式很简单：

```
[4字节 header_size][Proto序列化的 RpcHeader][Proto序列化的请求/响应参数]
```

`RpcHeader` 是 protobuf 消息，包含三个字段：`service_name`、`method_name`、`args_size`。

不用 HTTP 的原因：RPC 是内部服务间通信，不需要 HTTP 那些冗余的头部信息（Cookie、Header 等）。自定义二进制协议解析性能更高，带宽占用更少。我们只需要能唯一定位到某个服务的某个方法就够了。

### Q: 服务端收到一个 TCP 连接后，怎么把字节流还原成 RPC 调用？

**A:** 在 `RpcProvider::OnMessage()` 中（`src/mprpcprovider.cc`）：

1. 先读前 4 字节，拿到 `header_size`
2. 校验 `header_size` 合法性（不能超过 buffer 剩余数据量）
3. 读 `header_size` 字节，反序列化得到 `RpcHeader`，拿到 `service_name`、`method_name`、`args_size`
4. 再读 `args_size` 字节，根据 `service_name` + `method_name` 查 `m_serviceMap`，通过 protobuf 反射（`GetRequestPrototype(method).New()`）动态创建请求对象，反序列化填充
5. 同样通过反射创建响应对象，调用 `service->CallMethod(method, controller, request, response, done)` 分发到业务逻辑
6. 业务处理完后，`done->Run()` 触发 `SendRpcResponse()`，把响应反序列回同样的格式发回客户端

关键代码（`src/mprpcprovider.cc`）：

```cpp
// 解析 RpcHeader
std::string header_str(buf->peek(), header_size);
mprpc::RpcHeader rpcHeader;
rpcHeader.ParseFromString(header_str);

// 查服务和方法
auto it = m_serviceMap.find(rpcHeader.service_name());
const ServiceInfo& serviceInfo = it->second;
const auto& mit = serviceInfo.m_methodMap.find(rpcHeader.method_name());

// 反射创建请求/响应对象
auto request = serviceInfo.m_service->GetRequestPrototype(method).New();
auto response = serviceInfo.m_service->GetResponsePrototype(method).New();
request->ParseFromString(args_str);

// 动态分发
serviceInfo.m_service->CallMethod(method, controller, request, response, done);
```

### Q: 客户端怎么发起一次 RPC 调用？同步还是异步？

**A:** 客户端通过 `MprpcChannel::CallMethod()`（`src/mprpcchannel.cc`）发起调用，流程如下：

1. 序列化请求参数 → 组装 `RpcHeader` → 拼装成 `[4字节header_size][RpcHeader][args]` 的二进制包
2. 服务发现：查本地缓存或 ZooKeeper 获取服务地址 `ip:port`
3. 建立 TCP 连接（复用持久连接），发送数据
4. 阻塞等待响应（设置 5 秒接收超时），解析返回结果

虽然 `CallMethod` 的 `done` 参数支持异步（传入 closure），但我们的 consumer 示例传的是 `nullptr`，相当于同步阻塞调用。这个框架的网络层（Muduo）本身就是异步事件驱动的，但给业务方暴露的是同步接口。

### Q: 粘包问题怎么处理的？

**A:** 我们用 TL V（Type-Length-Value）方式。Muduo 的 `Buffer` 支持自动粘包处理。在 `OnMessage` 回调里：

```cpp
// 先判断 buffer 中可读数据是否 >= 4 字节
while (buf->readableBytes() >= sizeof(uint32_t)) {
    uint32_t header_size = *(uint32_t*)buf->peek();
    // 判断完整包是否到齐
    if (buf->readableBytes() >= header_size + 4) {
        buf->retrieve(4);  // 消费 header_size
        std::string header_str(buf->peek(), header_size);
        buf->retrieve(header_size);
        // 解析 args...
    } else break;
}
```

每次只消费一个完整包，剩余的留在 buffer 里等下一个 TCP 分片到达，天然解决粘包。

## 2. ZooKeeper 服务注册与发现

**简历描述：** 封装 ZooKeeper C API 实现服务注册与发现，利用临时节点 + Watcher 回调感知服务上下线，实现客户端本地缓存加速服务发现。

---

### Q: ZooKeeper 在这里扮演什么角色？

**A:** 作为服务注册中心。Provider 启动时将自身地址注册到 ZK，Consumer 通过 ZK 获取可用实例列表。ZK 的特性保证了服务的动态发现：临时节点会在会话断开时自动删除，Watcher 能实时通知变化。

### Q: ZK 节点结构怎么设计的？

**A:** 采用两级节点结构：

```
/{service_name}/{method_name}
```

数据内容为 `ip:port`，节点类型为**临时节点**（`ZOO_EPHEMERAL`）。Provider 启动时创建，断开时 ZK 自动删除。

关键代码（`src/mprpcprovider.cc`）：

```cpp
void RpcProvider::registerServicesToZK() {
    for (auto &sp : m_serviceMap) {
        std::string service_path = "/" + sp.first;
        m_zkclient.Create(service_path.c_str(), nullptr, 0);
        for (auto &mp : sp.second.m_methodMap) {
            std::string method_path = service_path + "/" + mp.first;
            char data[128] = {0};
            sprintf(data, "%s:%d", m_ip.c_str(), m_port);
            m_zkclient.Create(method_path.c_str(), data, strlen(data), ZOO_EPHEMERAL);
        }
    }
}
```

### Q: 客户端怎么发现服务？有缓存吗？

**A:** 在 `MprpcChannel::discoverService()`（`src/mprpcchannel.cc`）中：

1. 先查本地缓存 `m_addr_cache`，如果缓存未过期（30 秒 TTL），直接用缓存的 `ip:port`
2. 缓存过期或不存在，调用 `ZKClient::GetData()` 直接读取方法节点的数据（就是 `ip:port`）
3. 成功则更新缓存和 TTL 时间戳
4. 如果 ZK 不可用，降级用缓存中旧的地址

```cpp
std::string MprpcChannel::discoverService(const std::string& method_path) {
    // 查缓存
    {
        auto ts_it = m_cache_timestamps.find(method_path);
        if (ts_it != m_cache_timestamps.end()) {
            auto elapsed = std::chrono::duration_cast<std::chrono::seconds>(
                std::chrono::steady_clock::now() - ts_it->second).count();
            if (elapsed < CACHE_TTL_SEC) {
                auto addr_it = m_addr_cache.find(method_path);
                if (addr_it != m_addr_cache.end())
                    return addr_it->second;
            }
        }
    }
    // ZK 读取
    std::string addr = m_zkclient.GetData(method_path.c_str());
    if (!addr.empty()) {
        m_addr_cache[method_path] = addr;
        m_cache_timestamps[method_path] = std::chrono::steady_clock::now();
        return addr;
    }
    // 降级
    return m_addr_cache[method_path]; // 可能为空
}
```

### Q: ZK 连接断了怎么办？

**A:** ZKClient 封装了完整的重连机制（`src/zookeeperutil.cc`）：

1. **全局 Watcher** `global_watcher` 监听会话事件
2. **ZOO_EXPIRED_SESSION_STATE** 触发 `doReinitialize()`：
   ```cpp
   void ZKClient::doReinitialize() {
       zookeeper_close(m_zhandle);
       m_connected = false;
       sem_destroy(&m_sem);
       sem_init(&m_sem, 0, 0);
       Start();  // 重新 init 连接
       if (m_on_reconnect_cb) m_on_reconnect_cb();  // 回调重新注册服务
   }
   ```
3. Provider 注册了 `m_on_reconnect_cb`，重连后自动将本实例的所有服务重新注册到 ZK
4. `Start()` 用 `sem_timedwait()` 等待 5 秒超时，避免无限阻塞

### Q: 客户端发现 ZK 挂了，调用会失败吗？

**A:** 不会。客户端有**降级策略**（`src/mprpcchannel.cc` `discoverService()`）：

1. 优先查本地缓存（30 秒有效期），缓存命中直接使用
2. 缓存未命中 → 尝试 ZK `GetData()`，如果 ZK 不可用则查本地缓存
3. ZK 读取失败时，会重试 3 次（指数退避 1s/2s/4s + 随机抖动）
4. 最终兜底：只要以前成功获取过地址，缓存中就有，下次直接复用

## 3. 封装 hiredis 实现通用 Redis 客户端

**简历描述：** 封装 hiredis 实现通用 Redis 客户端，使用 mutex 保证线程安全，支持断线自动重连。

---

### Q: RedisClient 是怎么封装 hiredis 的？

**A:** `RedisClient`（`src/redisutil.h/cc`）封装了 hiredis 的 C API，提供面向对象的接口。支持常用的 Redis 数据类型：String、Hash、List、Set、ZSet，以及 Lua 脚本执行。

构造函数接收 `ip:port:password`，`Connect()` 方法调用 `redisConnectWithTimeout()` 建立连接，如果配置了密码则调用 `AUTH` 命令认证。

### Q: 线程安全怎么保证的？

**A:** 采用**两级策略**：

1. **主线程上下文 `m_context`**：用 `mutex` 加锁保护
2. **Worker 线程上下文 `t_context`**：`thread_local` 变量，每个线程首次使用时懒加载创建自己的连接

```cpp
redisContext* RedisClient::getContext() {
    if (t_context) return t_context;           // 已有 thread_local 连接
    if (!m_ip.empty()) {
        t_context = redisConnectWithTimeout(m_ip.c_str(), m_port, m_timeout);
        if (m_password.size() > 0) Auth(t_context);
        return t_context;
    }
    std::lock_guard<std::mutex> lock(m_mtx);
    return m_context;  // 主线程用共享连接
}
```

这样高并发的 worker 线程各自用独立连接，不需要抢锁，大幅降低锁竞争。

### Q: 断线重连怎么做的？

**A:** 每次执行 Redis 命令前调用 `ensureConnected()`：

```cpp
bool RedisClient::ensureConnected() {
    redisContext* ctx = getContext();
    if (!ctx || ctx->err) {
        Reconnect();
        return false;
    }
    return true;
}
```

如果发现连接异常，`Reconnect()` 会释放旧连接、重新 `Connect()`，并调用重连回调通知上层。上层（RateLimiter/MetricsCollector）注册了 `on_reconnect_cb` 用于恢复状态。

### Q: 断线期间上层调用会怎样？

**A:** RateLimiter（`src/ratelimiter.cc`）和 MetricsCollector 都加了保护：

```cpp
bool RateLimiter::allow(...) {
    if (!m_redis || !m_redis->EnsureConnected()) {
        return true;  // Redis 不可用时，放行所有请求（降级）
    }
    // ... 正常限流逻辑
}
```

**优雅降级：** Redis 挂了 → 不限流 + 不采集指标，业务调用不受影响。

## 4. 分布式限流算法

**简历描述：** 基于 Redis + Lua 脚本实现分布式令牌桶与滑动窗口限流算法，支持按服务/方法/来源 IP 多级粒度控制请求量。

---

### Q: 你们实现了哪几种限流算法？默认用哪个？

**A:** 实现了 5 种，通过配置文件 `ratelimitalgorithm` 选择（`src/ratelimiter.cc`）：

| 编号 | 算法 | 原理 | 特点 |
|------|------|------|------|
| 0 | Fixed Window | Redis `INCR` + `EXPIRE` | 实现简单，窗口边界有突发流量问题 |
| 1 | Sliding Window Log | ZSet 存储时间戳 | 最精确，内存占用高 |
| 2 | Sliding Window Counter | 10 个连续子窗口求和 | 精度和内存的折中 |
| **3** | **Token Bucket** | Redis Hash 存 `tokens` + `last_refill` | **默认**，允许突发流量 |
| 4 | Leaky Bucket | Redis List 做队列 | 平滑处理，队列满丢弃 |

### Q: 令牌桶具体怎么实现的？能详细说说 Lua 脚本吗？

**A:** 用 Redis Hash 存储两个字段：`tokens`（当前令牌数）和 `last_refill`（上次补充时间）。Lua 脚本保证原子性（`src/ratelimiter.cc`）：

```lua
local key = KEYS[1]
local capacity = tonumber(ARGV[1])    -- 最大令牌数
local rate = tonumber(ARGV[2])       -- 每秒补充速率
local now = tonumber(ARGV[3])        -- 当前时间戳(ms)

local bucket = redis.call('HGETALL', key)
local tokens = capacity
local last_refill = now

if #bucket > 0 then
    tokens = tonumber(bucket[2])
    last_refill = tonumber(bucket[4])
    -- 计算时间差，补充令牌
    local elapsed = now - last_refill
    local new_tokens = elapsed * rate / 1000.0
    if new_tokens > 0 then
        tokens = math.min(capacity, tokens + new_tokens)
        last_refill = now
    end
end

if tokens >= 1 then
    redis.call('HMSET', key, 'tokens', tokens - 1, 'last_refill', last_refill)
    redis.call('EXPIRE', key, 10)
    return 1  -- 放行
else
    return 0  -- 拒绝
end
```

容量 `capacity = max_requests`，速率 `rate = max_requests / window_sec`。比如配置 `maxqps=1000`、`window=1s`，则 capacity=1000、rate=1000/s。

### Q: 多级粒度的限流怎么实现的？

**A:** Redis key 的命名规则分级：

```
mprpc:ratelimit:{service_name}:{method_name}[:{client_ip}]:{suffix}
```

- **服务级：** `mprpc:ratelimit:UserServiceRpc:*`
- **方法级：** `mprpc:ratelimit:UserServiceRpc:Login:*`
- **来源 IP 级：** `mprpc:ratelimit:UserServiceRpc:Login:192.168.1.1:*`

Provider 端在 `OnMessage()` 解析出 `service_name`、`method_name` 和客户端 IP 后，调用 `m_rate_limiter->allow(service_name, method_name, client_ip)`。Consumer 端在 `CallMethod()` 发起调用前也做限流，形成双层保护。

### Q: 固定窗口和滑动窗口有什么区别？你们怎么选型？

**A:**
- **固定窗口**：每 1 秒重置计数器。缺点是在窗口边界可能出现 2 倍流量的突发（比如第 0.9 秒用了 1000，第 1.1 秒又用了 1000）。优点是实现简单，只需要 `INCR` + `EXPIRE`。
- **滑动窗口日志**：在每个请求的时间戳记录到 ZSet，查询时删除窗口外的记录，统计窗口内数量。精确但每个请求都写 ZSet，内存开销大。
- **滑动窗口计数器**：把窗口分成 N 个子窗口（我们用了 10 个），每个子窗口独立计数。查询时汇总所有子窗口。精度不如日志但内存消耗小很多。

默认用令牌桶是因为它既能限制平均速率，又能容忍一定程度的突发（积攒的令牌可以一次性使用），最符合 RPC 调用的实际场景。

## 5. 监控数据采集

**简历描述：** 通过 Redis INCR/ZSet 按分钟聚合 RPC 调用量、错误率与 P99 延迟采样，搭建基础监控数据采集层。

---

### Q: 指标数据是怎么组织存储的？

**A:** Redis Key 按分钟聚合（`src/metricscollector.cc`）：

```
mprpc:metrics/{service}/{method}:calls:{YYYYMMDD-HHMM}    // 调用量 (String, INCR)
mprpc:metrics/{service}/{method}:errors:{YYYYMMDD-HHMM}   // 错误量 (String, INCR)
mprpc:metrics/{service}/{method}:blocked:{YYYYMMDD-HHMM}  // 被限流拦截量 (String, INCR)
mprpc:metrics/{service}/{method}:latency                   // 延迟采样 (ZSet)
```

`YYYYMMDD-HHMM` 是分钟粒度的时间戳，每条记录设 TTL=3600 秒。

### Q: 延迟 P99 是怎么计算的？是全量采样吗？

**A:** 不是全量采样，是**1/10 采样**，避免高并发下写 Redis 太频繁：

```cpp
void MetricsCollector::recordCall(...) {
    incrWithExpire(call_key, 3600);
    if (rand() % 10 == 0) {  // 10% 采样率
        recordLatency(service, method, latency_ms);
    }
}
```

延迟数据存到 ZSet，score = 延迟毫秒数，member = `timestamp:random_id`。收集到一定量后，客户端可以 `ZRANGEBYSCORE` 排序后算 P99（取第 99% 分位的 score）。ZSet 会裁剪到最多 1000 条：

```cpp
m_redis->ZRemRangeByRank(key, 0, -1001);  // 保留最近 1000 条
m_redis->Expire(key, 3600);
```

### Q: 这些数据目前怎么展示？有监控面板吗？

**A:** 目前只是把数据写入了 Redis，属于**基础数据采集层**。上层可以对接 Grafana + Redis 数据源，或者写一个简单的定时任务从 Redis 读取数据推送到 Prometheus 等监控系统。项目主要聚焦在 RPC 框架本身，监控展示端属于后续可扩展的模块。

## 6. 熔断器与重试机制

**简历描述：** 实现客户端三态熔断器与指数退避重试机制，覆盖网络超时、序列化失败、服务不可达等异常场景。

---

### Q: 熔断器的状态机怎么设计的？

**A:** 三态模型（`mprpcchannel.h` `CircuitBreaker` 内部类）：

```
CLOSED  ──(连续失败 threshold 次)──▶  OPEN
  ▲                                      │
  │                           (30 秒后)
  │                                      ▼
  └──(HALF_OPEN 成功 1 次)───  HALF_OPEN
```

- **CLOSED**：正常状态，请求正常通过。每次失败计数递增
- **OPEN**：熔断开启，快速失败。30 秒超时后进入 HALF_OPEN
- **HALF_OPEN**：放行一个请求做探测。成功 → 回到 CLOSED（重置计数）；失败 → 回到 OPEN（重新计时）

```cpp
struct CircuitBreaker {
    atomic<int> failure_count{0};
    atomic<int> success_count{0};
    int threshold = 5;              // 连续 5 次失败触发熔断
    int timeout_ms = 30000;         // 30 秒后尝试恢复
    atomic<CircuitState> state{CLOSED};
    atomic<long long> last_failure_time{0};
};
```

### Q: 熔断粒度是怎样的？方法级别还是实例级别？

**A:** 目前是**方法级熔断**（`m_method_breakers`），key = `method_path`。连续 5 次调用失败后熔断该方法的调用，快速失败。熔断器实现的是三态状态机（CLOSED → OPEN → HALF_OPEN → CLOSED）。

之前有过实例级熔断器（每个 `ip:port` 独立熔断），配合多实例部署的 Round-Robin 负载均衡使用。取消多实例部署后，统一使用方法级熔断，设计更简洁。

### Q: 重试机制怎么实现的？最多重试几次？

**A:** 在 `CallMethod` 中的重试循环（`src/mprpcchannel.cc`），最多重试 3 次，总超时 8 秒：

```cpp
for (int attempt = 0; attempt < MAX_RETRY; ++attempt) {
    // 1. 检查方法级熔断器
    // 2. 服务发现（缓存优先）
    // 3. TCP 连接 + 发送
    // 4. 接收响应
    if (成功) {
        m_method_breakers[method_path].onSuccess();
        return;
    }
    // 失败：关闭连接，method 熔断器计数++
    continue;
}
```

每次重试会重新执行服务发现（可能拿到缓存中同一地址），通过总超时 8 秒控制避免无限等待。

### Q: 重试会引发雪崩吗？怎么防止的？

**A:** 我们的保护措施：
1. **熔断器**：方法连续失败 5 次后触发熔断，快速失败，减轻下游压力
2. **限流前置**：重试之前先过限流器，如果客户端自己已经超限了，直接快速失败
3. **有限重试**：最多 3 次 + 8 秒总超时，不是无限重试

但坦白说，目前没有**指数退避**（重试间隔没有逐渐增大），这是一个可以优化的点。

## 7. 异步日志引擎与错误码体系

**简历描述：** 实现线程安全异步日志引擎（生产者-消费者模型，mutex + condition_variable），设计三级结构化错误码体系（框架/系统/业务）。

---

### Q: 异步日志怎么保证高性能？

**A:** 采用**生产者-消费者模型**（`src/Logger.cc` + `src/lockqueue.h`）：

- **生产者**（业务线程）：调用 `LOG_INFO` 宏，把格式化后的日志字符串 push 到 `LockQueue`
- **消费者**（独立后台线程）：从 `LockQueue` pop，写入文件

`LockQueue` 的 `Pop()` 在没有数据时阻塞等待，不消耗 CPU：

```cpp
T Pop() {
    std::unique_lock<std::mutex> lock(m_mutex);
    while (m_queue.empty()) {
        m_cond.wait(lock);  // 没有日志时休眠
    }
    T data = m_queue.front();
    m_queue.pop();
    return data;
}
```

`Push()` 后调用 `notify_one()` 唤醒消费者线程。写入操作在消费者线程中完成，业务线程几乎不阻塞（只有 push 队列时的短暂加锁）。

### Q: 这个 LockQueue 和有锁队列比性能怎么样？有没有想过用无锁队列？

**A:** 当前的 `LockQueue` 基于 `std::queue` + `mutex` + `condition_variable`，在日志量不大的场景下完全够用。瓶颈一般在磁盘 IO 而不是锁竞争。

如果要优化，可以用**环形缓冲区（Ring Buffer）+ CAS 无锁队列**，避免锁竞争。但这个项目是学习性质，目前的有锁实现简单正确，且满足需求。项目中如果用 `LOG_INFO` 写日志的频率很高（比如每次 RPC 调用都写），无锁队列确实能减少性能损耗。

### Q: 三级错误码体系怎么设计的？

**A:** 枚举定义在 `src/include/rpcerror.h`：

| 层级 | 范围 | 用途 | 示例 |
|------|------|------|------|
| FrameErrorCode | 1xxx | 框架运行时错误 | 1001=超时, 1007=连接失败, 1008=无效 RPC 头 |
| SystemErrorCode | 2xxx | 系统资源错误 | 2001=节点过载, 2002=内存不足 |
| BusinessErrorCode | 3xxx | 业务逻辑错误 | 3001=参数校验失败, 3002=权限不足 |

`RpcError` 类组合了 `ErrorCode`（主码、子码、模块 ID）、`error_msg`、`node_ip:port`、`trace_id`、`stack_summary`，通过 `toString()` 输出结构化错误报告。

### Q: 实际使用中怎么区分这三种错误？

**A:** 以 consumer 调用为例（`example/caller/calluserservice.cc`）：

```cpp
// 先判断框架错误（网络超时、序列化失败等）
if (controller.Failed()) {
    LOG_ERROR("RPC failed: %s", controller.ErrorText().c_str());
    return;
}
// 再判断业务错误
if (response.result().errorcode() != 0) {
    LOG_ERROR("Business error: %s", response.result().errormsg().c_str());
}
```

`MprpcChannel` 设置框架错误（如 `MESSAGE_SEND_FAILED`），业务 Service 设置业务错误（如 `PERMISSION_DENIED`），两者互不干扰，调用方可以分段处理。

## 8. C++11 特性使用

**简历描述：** 基于 C++11 标准开发（智能指针、lambda、atomic、chrono、thread），CMake 构建产出静态库供多节点部署。

---

### Q: 项目中哪些地方用了 C++11 特性？举几个具体例子。

**A:**

| 特性 | 使用位置 | 用途 |
|------|----------|------|
| `std::unique_ptr` | `MprpcChannel` 中管理 `RedisClient`、`MetricsCollector`、`RateLimiter` | 自动生命周期管理，无需手动 delete |
| `std::shared_ptr` | `RpcProvider` 和 `MprpcChannel` 共享 `RedisClient` | 多个组件共享同一 Redis 连接 |
| `std::atomic` | `CircuitBreaker` 的 `failure_count`、`state` | 无锁线程安全计数 |
| `std::thread` + `lambda` | `Logger` 构造函数中启动后台写日志线程 | 分离的消费者线程 |
| `std::chrono` | 超时控制、RTT 延迟计算、ZSet 时间戳 | 高精度时间测量 |
| `thread_local` | `RedisClient` 中每个 worker 线程独立连接 | 避免锁竞争 |
| `std::mutex` + `std::condition_variable` | `LockQueue` 线程安全队列 | 生产者-消费者同步 |
| `nullptr` | 全面替代 `NULL` | 类型安全 |
| `override` | 所有继承的虚函数 | 编译期检查重写正确性 |

### Q: 为什么产出静态库而不是动态库？

**A:** 静态库（`libmprpc.a`）链接到目标可执行文件中，部署时不需要额外携带 `.so` 文件。在多节点部署场景下，每个节点只需要一个可执行文件即可运行，降低部署复杂度。另外静态库避免了动态库版本冲突的问题（"DLL Hell"）。

CMake 编译命令：

```cmake
# src/CMakeLists.txt
add_library(mprpc STATIC ${SRCS})
target_link_libraries(mprpc muduo_net muduo_base pthread zookeeper_mt hiredis protobuf)
```

## 9. ZooKeeper 高可用设计

**简历描述：** 在 `docxs/` 中有独立的 ZooKeeper 容错与多实例部署设计文档。

---

### Q: ZooKeeper 重连时，已经注册的服务信息怎么恢复？

**A:** `RpcProvider` 在初始化时设置了重连回调：

```cpp
m_zkclient.SetReconnectCallback([this]() {
    registerServicesToZK();
    LOG_INFO("ZK reconnected, services re-registered");
});
```

`registerServicesToZK()` 遍历 `m_serviceMap` 中的所有服务和方法，重新创建 ZK 临时节点。因为 ZK 会话过期后临时节点会被自动删除，所以重连后必须重新注册。`Create()` 已支持节点已存在时更新数据（`zoo_set`），避免快速重启时的冲突。

### Q: 你们的 ZK 节点是临时节点，如果 Provider 重启很快，ZK 会话还没过期怎么办？

**A:** `Create()` 里做了处理：如果节点已存在（旧会话的 ephemeral 节点还在），不会报错，而是调用 `zoo_set()` 更新节点数据。这保证了快速重启时新地址能正确写入，同时服务不会中断——因为这期间 Consumer 的本地缓存还在有效期内，会继续使用缓存的旧地址。

### Q: 你们有没有考虑过 ZK 本身的高可用？如果 ZK 集群挂了怎么办？

**A:** 我们项目里 ZK 是单节点部署的（学习环境）。如果 ZK 集群整体不可用：

1. **Provider 端**：无法注册服务，但已经启动的服务不受影响，继续处理请求
2. **Consumer 端**：如果本地缓存了实例地址，继续用缓存；如果缓存也没有且 ZK 不可用，调用失败返回 `SERVICE_DISCOVERY_FAILED`

生产环境应当部署 ZK 3 节点集群 + 在 Consumer 端设置更长的缓存 TTL + 增加持久化地址配置作为最后保底。

## 10. 整体架构与设计权衡

### Q: 这个项目你遇到的最大挑战是什么？怎么解决的？

**A:** 最大的挑战是**调用链路长、涉及组件多**。一个 RPC 请求从客户端到服务端经过：序列化 → 限流 → 服务发现 → 熔断检查 → TCP 连接 → 网络传输 → 服务端限流 → 反序列化 → 业务逻辑 → 序列化回响应。任何一个环节失败都要有合理的处理策略。

解决思路：
1. **分层设计**：每个组件职责单一（限流只管限流、熔断只管熔断），通过依赖注入组合
2. **全面降级**：每个外部依赖（ZK、Redis）不可用时都有 fallback 策略，不让单点故障拖垮整体
3. **结构化错误**：3 级错误码体系让问题定位更精确

### Q: 你觉得项目还有什么可以改进的地方？

**A:** 项目目前是学习性质，如果要上生产，有几个方向可以优化：

1. **线程模型**：`MprpcChannel` 不是线程安全的，QPS 测试里每个线程独立创建 channel。可以改为连接池模式，复用 channel
2. **无锁日志**：LockQueue 可以换成无锁环形缓冲区，进一步降低日志对业务线程的影响
3. **异步非阻塞**：目前 Consumer 的 `CallMethod` 是同步阻塞的，可以改成完全异步的回调模式
4. **链路追踪**：`RpcError` 里虽然有 `trace_id`，但还没有完整的链路追踪系统
5. **配置中心**：目前是本地配置文件，改成远程配置中心可以动态调整限流阈值、熔断参数
6. **Protobuf 版本**：由 `proto2` / `proto3` 未明确指定，应显式声明
