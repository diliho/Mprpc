# 多实例部署：同一服务方法注册到不同 IP:Port

## 当前实现分析

### 结论：不支持

当前 MPRPC 项目**不支持**将同一个远程服务方法注册到多个不同的 IP:Port 上。

### 原因

**Provider 端** — `registerServicesToZK()` 中：

```cpp
// mprpcprovider.cc:55-70
void RpcProvider::registerServicesToZK()
{
    for (auto &sp : m_serviceMap)
    {
        std::string service_path = "/" + sp.first;
        m_zkclient.Create(service_path.c_str(), nullptr, 0);
        for (auto &mp : sp.second.m_methodMap)
        {
            std::string method_path = service_path + "/" + mp.first;
            //                   ↑  每个方法只创建一个固定路径的节点
            //                       如 /UserServiceRpc/Login
            char method_path_data[128] = {0};
            sprintf(method_path_data, "%s:%d", m_ip.c_str(), m_port);
            m_zkclient.Create(method_path.c_str(), method_path_data,
                              strlen(method_path_data), ZOO_EPHEMERAL);
            //      ↑  如果节点已存在（另一个 Provider 创建的），zoo_exists
            //          检查到存在 → 跳过创建 → 第二个 Provider 的地址不会注册
        }
    }
}
```

`ZKClient::Create()` 中的去重逻辑：

```cpp
// zookeeperutil.cc
flag = zoo_exists(m_zhandle, path, 0, nullptr);
if (ZNONODE == flag) {
    flag = zoo_create(m_zhandle, path, ...);  // 仅当节点不存在时才创建
}
```

**Consumer 端** — `discoverService()` 中：

```cpp
// mprpcchannel.cc
std::string host_data = m_zkclient.GetData(method_path.c_str());
//                   ↑ 从固定路径 /UserServiceRpc/Login 读一个地址
//                     无论有多少 Provider，只能读到其中一个
```

### 后果

```
部署拓扑（当前）：
┌──────────────────┐      ┌──────────────────┐
│  Provider A      │      │  Provider B      │
│  192.168.1.1:8000│      │  192.168.1.2:8000│
└────────┬─────────┘      └────────┬─────────┘
         │                         │
         ▼                         ▼
  创建 /UserServiceRpc/Login    创建 /UserServiceRpc/Login
  → "192.168.1.1:8000"           → 节点已存在，跳过！
         │
         ▼
 ZK 上只有 /UserServiceRpc/Login → "192.168.1.1:8000"
 Provider B 永远不会被 Consumer 发现！
```

## 最优设计方案

### ZK 节点结构改造

将单节点改为 **父节点 + 多子节点** 结构：

```
改造前（单实例）：
/UserServiceRpc/Login  →  "192.168.1.1:8000"

改造后（多实例）：
/UserServiceRpc/Login
    ├── 0000000001  →  "192.168.1.1:8000"  临时顺序节点
    ├── 0000000002  →  "192.168.1.2:8000"  临时顺序节点
    └── 0000000003  →  "192.168.1.3:8000"  临时顺序节点
```

### 核心技术点

| 技术 | 说明 |
|------|------|
| **临时顺序节点** | `ZOO_EPHEMERAL \| ZOO_SEQUENCE` — Provider 断开时自动删除，ZK 自动编号 |
| **获取子节点列表** | `zoo_get_children()` — Consumer 获取所有在线实例 |
| **负载均衡策略** | 从子节点列表中按策略选择一个 |

### Provider 端改造

```cpp
// mprpcprovider.cc
void RpcProvider::registerServicesToZK()
{
    for (auto &sp : m_serviceMap)
    {
        std::string service_path = "/" + sp.first;
        m_zkclient.Create(service_path.c_str(), nullptr, 0);   // 持久节点
        for (auto &mp : sp.second.m_methodMap)
        {
            std::string method_path = service_path + "/" + mp.first;

            // ① 创建服务级别的持久节点作为目录（如果不存在）
            m_zkclient.Create(method_path.c_str(), nullptr, 0);

            // ② 在方法节点下创建临时顺序子节点
            //    自动生成唯一后缀，不会冲突
            std::string child_path = method_path + "/instance-";
            char data[128];
            sprintf(data, "%s:%d", m_ip.c_str(), m_port);
            m_zkclient.CreateSequential(child_path.c_str(), data,
                                        strlen(data), ZOO_EPHEMERAL);
        }
    }
}
```

新增 `ZKClient::CreateSequential()`：

```cpp
// zookeeperutil.h
class ZKClient {
public:
    void CreateSequential(const char* base_path, const char* data,
                          int datalen, int state);
};

// zookeeperutil.cc
void ZKClient::CreateSequential(const char* base_path, const char* data,
                                 int datalen, int state)
{
    if (!m_zhandle || !m_connected)
    {
        LOG_ERROR("ZK not connected, cannot create sequential node: %s", base_path);
        return;
    }

    char path_buffer[256];
    int bufferlen = sizeof(path_buffer);
    // ZOO_SEQUENCE 让 ZK 自动在路径后追加递增序号
    int flag = zoo_create(m_zhandle, base_path, data, datalen,
                          &ZOO_OPEN_ACL_UNSAFE, state | ZOO_SEQUENCE,
                          path_buffer, bufferlen);
    if (flag == ZOK)
    {
        LOG_INFO("SUCCESS: Create sequential znode: %s", path_buffer);
    }
    else
    {
        LOG_ERROR("Create sequential znode failed: %s, error code: %d",
                  base_path, flag);
    }
}
```

### Consumer 端改造

```cpp
// mprpcchannel.h
class MprpcChannel : public google::protobuf::RpcChannel
{
    // 新增：负载均衡策略
    enum class LBStrategy { RANDOM, ROUND_ROBIN };
    LBStrategy m_lb_strategy = LBStrategy::ROUND_ROBIN;
    std::unordered_map<std::string, std::atomic<uint64_t>> m_rr_indices;
};
```

改造 `discoverService()`：

```cpp
// mprpcchannel.cc
std::string MprpcChannel::discoverService(const std::string& method_path)
{
    // 1. 优先从 ZK 获取实例列表
    if (m_zk_available)
    {
        for (int i = 0; i < MAX_RETRY; ++i)
        {
            std::vector<std::string> instances = getInstancesFromZK(method_path);
            if (!instances.empty())
            {
                std::string selected = selectInstance(method_path, instances);
                setCachedAddress(method_path, selected);
                return selected;
            }
            // 退避重试
            if (i < MAX_RETRY - 1) {
                usleep(((1000 << i) + rand() % 500) * 1000);
            }
        }
        m_zk_available = false;
    }

    // 2. 降级到缓存（保留单个地址）
    return getCachedAddress(method_path);
}

// 从 ZK 获取所有在线实例
std::vector<std::string> MprpcChannel::getInstancesFromZK(
    const std::string& method_path)
{
    std::vector<std::string> instances;

    // 获取所有子节点名称
    struct String_vector children;
    int rc = zoo_get_children(m_zkclient.getHandle(),
                              method_path.c_str(), 0, &children);
    if (rc != ZOK) return instances;

    // 读取每个子节点的数据（IP:Port）
    for (int i = 0; i < children.count; ++i)
    {
        std::string full_path = method_path + "/" + children.data[i];
        std::string addr = m_zkclient.GetData(full_path.c_str());
        if (!addr.empty()) {
            instances.push_back(addr);
        }
    }
    deallocate_String_vector(&children);

    return instances;
}

// 负载均衡选择
std::string MprpcChannel::selectInstance(
    const std::string& method_path,
    const std::vector<std::string>& instances)
{
    if (instances.empty()) return "";
    if (instances.size() == 1) return instances[0];

    switch (m_lb_strategy)
    {
    case LBStrategy::RANDOM:
        return instances[rand() % instances.size()];

    case LBStrategy::ROUND_ROBIN:
    {
        uint64_t idx = m_rr_indices[method_path]++ % instances.size();
        return instances[idx];
    }
    }
    return instances[0];
}
```

### 熔断器适配多实例

熔断器需要从"方法级"细化到"实例级"：

```cpp
// mprpcchannel.h
class MprpcChannel {
    // key: "method_path@ip:port"  →  每个实例独立熔断
    std::unordered_map<std::string, CircuitBreaker> m_instance_circuit_breakers;
};
```

调用流程变为：

```
1. getInstancesFromZK → ["192.168.1.1:8000", "192.168.1.2:8000"]
2. 对每个实例检查熔断器，过滤已熔断的
3. 从可用实例中负载均衡选一个
4. 连接失败 → 该实例熔断器记录失败
5. 切换到下一个可用实例
6. 全部熔断 → 方法级熔断器 OPEN
```

```cpp
std::string MprpcChannel::selectAliveInstance(
    const std::string& method_path,
    const std::vector<std::string>& instances)
{
    std::vector<std::string> alive;
    for (auto& addr : instances)
    {
        std::string cb_key = method_path + "@" + addr;
        std::lock_guard<std::mutex> lock(m_cb_mtx);
        if (m_instance_circuit_breakers[cb_key].allowRequest()) {
            alive.push_back(addr);
        }
    }
    if (alive.empty()) return "";
    return selectInstance(method_path, alive);  // 从存活实例中选
}
```

### ZK 节点变化自动感知

Consumer 通过 ZK Watcher 感知实例上下线，无需每次调用都查询：

```cpp
// 在 MprpcChannel 初始化时注册 Watcher
void MprpcChannel::watchMethodNode(const std::string& method_path)
{
    zoo_wget_children(m_zkclient.getHandle(), method_path.c_str(),
                      childrenWatcher, this, nullptr);
}

// Watcher 回调：实例变化时自动刷新缓存
static void childrenWatcher(zhandle_t* zh, int type, int state,
                             const char* path, void* ctx)
{
    if (type == ZOO_CHILD_EVENT)
    {
        MprpcChannel* channel = static_cast<MprpcChannel*>(ctx);
        channel->refreshInstanceCache(path);
        // 重新注册 Watcher（一次性触发后需要重新注册）
        channel->watchMethodNode(path);
    }
}

// 刷新实例缓存（后台更新，不影响正在进行的调用）
void MprpcChannel::refreshInstanceCache(const std::string& method_path)
{
    std::vector<std::string> instances = getInstancesFromZK(method_path);
    // 更新本地缓存
    std::lock_guard<std::mutex> lock(m_cache_mtx);
    m_instance_cache[method_path] = instances;
}
```

```
Provider A 启动                    Provider B 启动
    │                                  │
    ▼                                  ▼
创建 /UserServiceRpc/Login         创建 /UserServiceRpc/Login
  (持久节点，已存在则跳过)             (已存在，跳过)
    │                                  │
    ▼                                  ▼
创建 /UserServiceRpc/Login/        创建 /UserServiceRpc/Login/
  instance-0000000001                 instance-0000000002
  → "192.168.1.1:8000"               → "192.168.1.2:8000"
    │                                  │
    └──────────────┬───────────────────┘
                   ▼
    ZK 节点状态：
    /UserServiceRpc/Login
        ├── instance-0000000001 → "192.168.1.1:8000"
        └── instance-0000000002 → "192.168.1.2:8000"

Consumer 发起调用
    │
    ▼
zoo_get_children("/UserServiceRpc/Login")
    │
    ▼
["instance-0000000001", "instance-0000000002"]
    │
    ▼
读取数据 → ["192.168.1.1:8000", "192.168.1.2:8000"]
    │
    ▼
负载均衡选一个（轮询/随机）

    │

    │
    ▼

→ ["192.168.1.2:8000"]
→ 后续请求全部路由到 Provider B
```

## 优雅关闭适配

多实例下，优雅关闭时同样需要清理：

```cpp
// mprpcprovider.cc — handleSigInt
static void handleSigInt(int)
{
    if (!g_shutdown_provider) return;
    LOG_INFO("Received SIGINT, shutting down gracefully...");

    ZKClient& zk = g_shutdown_provider->getZkClient();
    zk.setOnReconnectCallback(nullptr);

    if (zk.getHandle())
    {
        for (auto &sp : g_shutdown_provider->getServiceMap())
        {
            for (auto &mp : sp.second.m_methodMap)
            {
                // 先获取本 Provider 创建的子节点列表
                std::string method_path = "/" + sp.first + "/" + mp.first;
                String_vector children;
                if (zoo_get_children(zk.getHandle(), method_path.c_str(),
                                     0, &children) == ZOK)
                {
                    for (int i = 0; i < children.count; ++i)
                    {
                        std::string full = method_path + "/" + children.data[i];
                        std::string data = zk.GetData(full.c_str());
                        if (data == g_shutdown_provider->getAddress())
                        {
                            zoo_delete(zk.getHandle(), full.c_str(), -1);
                            LOG_INFO("Deleted ZK node: %s", full.c_str());
                        }
                    }
                    deallocate_String_vector(&children);
                }
            }
        }
    }
    g_shutdown_provider->getEventLoop().quit();
}
```

## 多实例带来的额外收益

### 1. 滚动升级（零停机）

```
步骤：
1. 启动 Provider B（新版本），注册到 ZK
2. Consumer 开始将部分请求路由到 B
3. 优雅关闭 Provider A（旧版本），ZK 节点删除
4. Consumer 全部路由到 B
5. 升级 A 并重启，注册到 ZK
6. Consumer 自动开始路由到 A

→ 整个过程 Consumer 无感知，零停机！
```

### 2. 灰度发布（金丝雀部署）

```
/UserServiceRpc/Login
    ├── instance-0000000001  → "192.168.1.1:8000"  ← 稳定版本
    ├── instance-0000000002  → "192.168.1.2:8000"  ← 稳定版本
    └── instance-0000000003  → "192.168.1.3:8000"  ← 金丝雀版本（新代码）

Consumer 端对金丝雀实例加权：
→ 95% 请求到稳定版本
→ 5% 请求到金丝雀版本
→ 观察无异常后逐步放量
```

### 3. 容量扩缩容

```
高峰期：启动 10 个 Provider → Consumer 自动利用全部
低谷期：关闭 8 个 Provider → Consumer 自动减少连接

→ 弹性伸缩，按需使用资源
```

## 与现有容错机制的整合

多实例部署与项目中已有的容错机制可以无缝配合：

| 已有容错 | 多实例下如何配合 |
|---------|----------------|
| 熔断器 | 实例级熔断器：单个实例连续失败 5 次后只熔断该实例，不影響其他实例 |
| 缓存 | 缓存实例列表而非单个地址；实例变化时 Watcher 自动更新缓存 |
| 重试+退避 | 失败后切换到下一个可用实例重试，而非等待退避后重试同一个 |
| 超时控制 | 单个实例超时时快速切换到下一个，无需等待整体超时 |
| 优雅关闭 | 关闭前删除自己的顺序节点，Consumer Watcher 立即感知，路由到其他实例 |
| Provider 错误回复 | 单个实例返回错误时，Consumer 切换到下一个实例重试 |

### 多实例调用决策流

```
CallMethod 开始
    │
    ├── ① 检查方法级熔断器
    │     └── OPEN → 快速失败
    │
    ├── ② 获取实例列表（ZK / 缓存）
    │
    ├── ③ 过滤已熔断的实例
    │
    ├── ④ 负载均衡选一个实例
    │
    ├── ⑤ 检查该实例的熔断器
    │     └── OPEN → 回到 ④ 选下一个
    │
    ├── ⑥ connect + send (带超时)
    │     └── 失败 → 该实例熔断器记录 + 回到 ④ 选下一个
    │
    ├── ⑦ recv (带超时)
    │     └── 超时/错误 → 该实例熔断器记录 + 回到 ④ 选下一个
    │
    └── ⑧ 成功 → 所有熔断器记录成功
```

## 方案对比

| 方案 | 实现复杂度 | Consumer 感知延迟 | ZK 节点数 | 适用场景 |
|------|-----------|------------------|-----------|---------|
| **子节点方案（推荐）** | 中 | 即时（Watcher 通知） | O(实例数 × 方法数) | 通用，适合大多数场景 |
| 单节点存多地址 `ip1:port1,ip2:port2` | 低 | 延迟（轮询查询） | O(方法数) | 实例少、变化不频繁 |
| 单节点存动态 DNS | 高（需 DNS 基础设施） | 取决于 DNS TTL | O(方法数) | 已有 DNS 服务发现 |

**推荐子节点方案**，原因：
- ZK 原生支持（临时顺序节点 + Child Watcher）
- 实例上下线即时感知
- 熔断器可以细化到实例级
- 每个实例独立管理，互不影响
